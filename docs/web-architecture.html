01 / Scope and decision status

This document defines the web application architecture and UX proposal. It extends the Phase 1 handbook without implementing the application. All wireframes are static, synthetic illustrations. Buttons shown in illustrations are labels, not functioning controls.

The full product is represented by an information architecture and roadmap. Only Phase 1 becomes an operational workspace initially. Future modules do not appear as empty daily-navigation destinations.

04 / Frontend and backend boundaries

Frontend: navigation, accessible interactions, user draft text, review selection, source viewing, and operation progress. Backend: workspace authorization, source persistence, interview policy, structured-output validation, explicit acceptance, revision tracking, and dependency invalidation.

Browser route guards improve UX but do not enforce data access. Every backend resource lookup, source download, graph query, and background operation enforces workspace ownership.

11 / Answer and AI operation protocol

  1. Client submits an answer with an operation key and expected session revision.
  2. Server verifies workspace access and stores the original turn transactionally.
  3. Server returns the saved turn, revision, and generation operation ID.
  4. An operation processes scoped context, calls the provider, and validates structured output and source IDs.
  5. Client observes operation status through SSE or polling. Generation completion persists a draft review, not accepted facts.
  6. User reviews specific facts and interpretations through explicit commands with expected revisions.
  7. Accepted revisions update the model and mark dependent interpretations as needed.

Transport retries reuse the same operation key. SSE disconnects do not erase saved turns or create duplicate model work; reconnect retrieves the persisted result. Cancelling generation does not delete an already saved answer. Polling provides a simpler fallback. An in-process executor is acceptable locally; hosted operation recovery requires durable operation state and a recoverable worker strategy.

Use consistent error codes and safe messages. Exact REST paths, DTOs, and validation schemas will be specified with the first implementation slice. Cross-workspace IDs must never expose private record content.

13 / Identity, privacy and environments

Local development may use an explicit development-only identity behind a localhost binding. Hosted private use requires real authentication and authorization before personal data are stored. Prefer same-origin secure cookie sessions with appropriate CSRF defenses; confirm the identity provider during implementation. Development shortcuts cannot be enabled in a public environment.

Use separate development, test, and production databases and storage. Synthetic fixtures only in source control. Model credentials stay in server secrets; logs exclude raw transcripts by default. Before external model processing, explain provider destination and content scope, allow redaction, and store the selected data policy.

Uploads can be deferred. When introduced, validate file size and type, protect downloads, treat extracted text as untrusted data, and define retention/deletion rules before allowing employer documents.
