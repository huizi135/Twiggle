01 / Purpose and product identity

Twiggle is the working product name, replacing EVIDENCE. Like a bird building a nest from individual twigs, people can build an understanding of themselves from specific experiences. The metaphor guides tone; it does not determine the data model.

The product helps people recover overlooked work, distinguish their own contribution from team outcomes, discover supported capabilities, and make revisable career decisions. Its first application is career development, with CV generation as a downstream output.

A structured profile is a revisable model, not an objective or complete definition of a person. Naming, domain availability, and trademark suitability remain unvalidated.

03 / Initial user and boundaries

Start with one software engineer exploring Backend & Cloud Applications, Real-Time & Connected Systems, and Test Automation & Release Engineering in Swiss Romandie. These are career hypotheses, not separate identities or validated market opportunities.

  • Capture professional, learning, volunteer, and personal-project experience, with their contexts kept distinct.
  • Model work authorization, geography, language, and mandatory credentials as feasibility constraints; do not reduce capability because a constraint is unmet.
  • Start with the founder’s Alsensia experience for usability, then a previously unexplored episode for discovery evaluation. Do not reuse known answers as proof of discovery.
  • Do not build a job board, automated application sender, personality classifier, or generic résumé rewriting chatbot.

Sequence is dependency-driven, not a calendar promise. Each phase has a design review, a small implementation slice, evaluation, and a release decision. Later phases remain more tentative.

05 / Shared product logic

Source → Experience Claim → Contextual Skill Claim → Decision. Preserve original material and its limitations. A user confirmation, artifact support, and completed work are independent attributes. Multiple summaries of the same source are not independent corroboration.

  • Record assertions individually; avoid one verified badge for an entire episode.
  • Show why a conclusion exists and what it does not establish. Unknown is valid.
  • Require review when a supporting claim changes. Exported historical documents remain historical snapshots and must be identified as outdated when reopened.
  • Preferences need context, time, and exceptions. Good performance does not imply enjoyment.
  • Current market demand must not steer the interview into inventing attractive skills.

07 / Cross-cutting engineering contract

  • Use stable IDs, explicit revisions, timestamps, and provenance links. Separate the date an event happened from the date it was recorded.
  • Treat source text and uploads as data, never as instructions to the AI orchestration layer.
  • Before sending content to an external model, show the destination and selected scope; minimize and redact employer/client details.
  • Keep secrets outside source control. Exclude real transcripts, uploaded artifacts, identifying telemetry, and local environment files from Git.
  • Support export, correction, and deletion. Auditability does not justify retaining deleted private content forever; remove payloads and derived indexes under a documented retention policy.
  • Measure extraction, question quality, attribution, support validity, correction propagation, latency, and cost. Avoid a single opaque confidence or fit score.
  • Documentation must distinguish hypotheses, implementation plans, tested behavior, and deployed behavior.

08 / Windows checkout and reading guide

Use Git for Windows and an account authorized for this private repository. These commands run on the user’s Windows computer, not in the remote documentation environment.

New-Item -ItemType Directory -Force "C:\Users\Admin\Documents\GitHub" | Out-Null
Set-Location "C:\Users\Admin\Documents\GitHub"
git clone https://github.com/huizi135/Twiggle.git
Set-Location Twiggle
Start-Process .\docs\index.html

If the checkout already exists, enter that directory, inspect git status, then use git pull --ff-only when appropriate. Do not overwrite local changes. All handbook pages work offline without a server, account, CDN, or build step.

09 / Open decisions and immediate work

  • Agree on Episode boundaries and the review experience before database migrations.
  • Run a manual interview using the proposed policy, recording why each question is selected.
  • Define a small evaluation set with hidden ground truth and explicit unsupported interpretations.
  • Decide whether artifact upload is needed for the first slice; transcript evidence is sufficient to test the core loop.
  • Review the Phase 1 field model and lifecycle. Then build one complete thin slice before expanding coverage.
Build from real experiences. Keep the evidence, uncertainty, and room to change.
