01 / Outcome and minimum product

Given an incomplete account of one event, ask useful non-leading questions, preserve the user’s actual contribution, propose bounded capability interpretations, and create a correctable capability brief with traceable sources.

Minimum journey: Tell a story → focus an episode → answer follow-ups → review facts and interpretations → save → inspect supporting sources → correct → see dependent conclusions updated.

Exclude job scraping, career-fit scoring, polished CV export, personality labels, graph algorithms, and multi-user administration. A basic relationship explorer belongs here; a complex animated network does not.

03 / Interview lifecycle

Capture → Scope → Explore ↔ Clarify → Review → Save
Any active state → Paused → previous state
Review → Explore when a material gap is found
Saved episode → new session or explicit revision
StateAction and transition condition
CapturePreserve original text; identify possible events without asserting skill ownership.
ScopePropose one bounded problem/action/outcome. User may keep a broad account or change focus.
ExploreAsk one primary question based on current gaps. Record why it was chosen.
ClarifyResolve uncertain ownership, ambiguous terminology, timeline conflicts, or material contradictions. Unknown remains allowed.
ReviewPresent a short factual account first, then separate capability proposals. Unreviewed fields remain pending.
SavePersist current reviewed and unresolved records with their own statuses. Save does not certify truth.
PausedPersist focus, already covered material, pending question, and continuation summary; resume without asking the whole interview again.

Stop when context, individual action, ownership, outcome/current state, and significant uncertainties permit a useful account, or when the user chooses to stop. Offer a short checkpoint after roughly 5–8 follow-ups as an initial UX hypothesis, not a mandatory quota.

04 / Question policy v0.1

Keep a question backlog with TargetGap, ProbeType, Rationale, ExpectedDecisionChange, PriorAttempts, and UserBurden. Prefer a rule-based ordering initially; do not invent numerical information-gain estimates.

PriorityTriggerExample
1 · Attribution / conflictA broad claim could incorrectly assign responsibility“Which steps did you personally change, and which were already in place?”
2 · Meaningful missing actionA tool name exists but no concrete behavior is known“What did the workflow do when a pull request was opened?”
3 · Depth / judgmentImplementation is known; decisions and constraints are unclear“What alternatives did you consider, if any?”
4 · Failure / outcomeNormal operation is described; actual usefulness is unclear“Can you recall one failure and what you did next?”
5 · Preference / transferEnough behavioral context exists for reflection“Which part of this work would you choose to do again, and under what conditions?”

Avoid “So you architected a release platform?” Ask for actions before supplying a skill label. If the user does not remember, try one neutral recall cue, then leave a gap. Do not repeatedly rephrase a skipped question unless the user reopens it.

Generic prompts work across domains; domain packs supply vocabulary and candidate follow-ups. A taxonomy suggests possibilities, not conclusions.

05 / Coverage and contradiction handling

Track Context, Problem, Ownership, Actions, Interfaces, Decisions, Failures, Quality, Outcomes, Evidence, Learning, and Preferences. Each dimension can be Unexplored, Partial, SufficientForCurrentGoal, Skipped, or NotApplicable, with source references and a reason. Coverage is local to an episode and goal.

For a conflict, preserve both statements, identify the possible scope difference, and ask neutrally: “Earlier you described designing the backend; now you mention a lead choosing the architecture. Which decisions were yours?” Record Contradiction or an open question until resolved. Do not silently choose the more impressive statement.

ActivityContext: Professional, Learning, Volunteer, PersonalProject. CompletionStatus: Planned, InProgress, Completed, Abandoned, Unknown. These are distinct from source support and user review. Date precision may be year, month, day, or approximate.

07 / Claim and evidence contract

A claim is an assertion small enough to accept, dispute, or revise independently. “I configured GitHub Actions” and “I independently designed the whole release architecture” must be different claims.

  • User review: Pending / Accepted / Disputed. Accepted means the user endorses the wording, not that an external verifier has certified it.
  • Source support: assessed per EvidenceLink. A workflow file may show behavior but cannot alone prove who authored it. A self-reported ownership claim remains self-reported.
  • AI origin is retained even after review. Inferred skill interpretations need explicit supporting actions and user review.
  • An unavailable source keeps its reference and access status; do not pretend it has just been inspected.
  • Store measurement value, unit, time window, baseline, and source when claiming quantified impact. Otherwise preserve a qualitative outcome.
  • Do not assign skill strength from edge count, confident wording, or the model’s self-reported probability.

09 / Graph model and revision behavior

The relational model is canonical for the current accepted interpretation. The graph is a projection: Project → Episode → Claim → Source, with SkillClaim → supporting Claim → Episode. Preferences point to episodes and context. Technology usage is a fact; it does not automatically imply mastery.

On correction: create a new claim revision → find dependent SkillClaims → mark affected interpretations NeedsReview → refresh graph projection → flag capability briefs based on superseded data. Preserve older report snapshots with their revision IDs. A deletion removes source payloads and invalidates derived records according to retention rules; a minimal tombstone must not retain deleted sensitive text.

10 / AI and application responsibilities

AI proposes: candidate claims, episode boundaries, possible skills, conflicts, and a next-question draft. Application enforces: allowed states, valid record references, source locators, review status changes, authorization, revision dependencies, and persistence.

Suggested logical API operations: create interview session; append turn with idempotency key and expected revision; get review draft; accept or edit specific claims; save episode; list capability support; revise or delete records; export personal model. Exact routes and DTOs are deferred until the field model is reviewed.

  • Use a provider adapter for structured model output. Reject missing or invalid references; never silently persist fabricated IDs.
  • Persist the user turn before model execution. On provider timeout, retain it and offer retry without duplicate turns.
  • Use optimistic concurrency for edits and an operation key for retries. Cancellation or partial output cannot promote a claim to accepted.
  • Retrieve only the active episode, relevant support, and session summary; retain exact source references when compressing context.
  • Record prompt/model versions, validation failures, latency, and cost without logging raw private text by default.

1.2 · Model reviewDefine entities, status dimensions, source locators, revisions, and deletion behavior; create synthetic fixtures.A planned project cannot become completed experience through review.
1.3 · Persistence sliceCreate project, episode, claim, source, and evidence storage; implement edit and export.Claims retain exact source links; revision conflict is handled.
1.4 · Interview sliceImplement session lifecycle and one structured AI extraction / follow-up pipeline.Retry preserves the answer; skipped questions do not loop; resume retains context.
1.5 · Review sliceBuild side-by-side quote / factual review and separate interpretation review.Accepting a fact does not automatically accept all proposed skills.
1.6 · Explorer sliceAdd episode explorer, skill support list, and small relationship view.Every capability can reveal ownership, sources, and limits.
1.7 · Correction sliceImplement dependency invalidation, updated projections, report revisions, and deletion.An ownership correction marks affected conclusions for review.
1.8 · ValidationRun held-out episodes and adversarial fixtures; compare policy versions; document failure cases.Meet release gates below before expanding scope.

Build one complete story-to-review-to-source journey before adding many taxonomies or UI filters. No dates are promised until manual discovery indicates realistic work size.

12 / Evaluation and provisional release gate

Case / measureExpected behavior
Known Alsensia storyEvaluate usability and reconstruction only; exclude already supplied facts from discovery gains.
Held-out unfamiliar episodeCompare initial account with the reviewed result; record genuinely new, behavior-supported capabilities.
Team accomplishmentNo promotion to individual ownership without clarification.
Planned deployment platformRemains Planned; cannot appear as completed implementation.
No measurable impactNo invented percentage, scale, time saving, or business outcome.
Contradictory / corrected ownershipConflict remains visible; dependent interpretations require review.
Skip, pause, timeout, deletionNo loops or lost accepted answers; retry is idempotent; deleted content leaves derived views.
Leading-question checkReviewer flags questions that suggest the desired answer; compare useful information gained per question.

Initial acceptance proposal: evaluate at least three bounded episodes, including one held-out episode, plus the failure cases above. All accepted SkillClaims must have valid claim and source paths; no fabricated responsibility, technology, or metric is allowed in released briefs. Any critical attribution error blocks release. A useful discovery is a previously unarticulated capability tied to concrete behavior, not a synonym added to an existing label.

Track user corrections, redundant-question rate, time to a useful brief, skipped topics, unresolved conflicts, latency, and cost. This small sample supports a prototype decision, not a general accuracy claim.

13 / Decisions to resolve before coding

  • Approve the manual interview policy and episode boundaries.
  • Choose whether first-release sources are transcript-only or include minimal uploads.
  • Set the external-model data handling and deletion policy.
  • Agree on English canonical terminology while preserving original-language source text.
  • Select concrete dependency versions and validate provider contracts against current official documentation at implementation time.
Build from real experiences. Keep the evidence, uncertainty, and room to change.
